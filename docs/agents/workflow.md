# 文档/发版/审查规范

## 文档

* 根 README 保持简洁（介绍/核心功能/快速开始/文档入口）。
* `docs/index.md` 为唯一全量索引；上游用户文档指路 `docs/upstream-summary.md`，不复制原文。
* 二次开发协作、架构和待办规则放根 `docs/`；产品使用说明放 `infinite-canvas/docs/`。不要把内部流程写进上游用户文档。
* 用户可见的产品改动，在 `infinite-canvas/CHANGELOG.md` 的 `Unreleased` 追加一句中文，按 `[新增]/[调整]/[修复]/[优化]` 分类；纯内部重构可不记。只改根协作文档时，不动产品 CHANGELOG。
* 上游 `docs/content/docs/progress/`（todo/pending-test）只记录上游事项；二次开发待办走 `docs/roadmap.md`。

## 发版

* 发版前核对产品 CHANGELOG、`infinite-canvas/VERSION`、构建/部署入口及发布范围；版本号跟随上游基线，二次开发产品版本另有约定时以明确决策为准。
* 产品 tag 指向 `infinite-canvas/` 的 subtree split，使发行树不包含根协作层；操作步骤见 `../git-branch-strategy.md`。
* 只有用户明确授权发布动作时才创建/推送 tag 或发布产物；本地文档任务不触发发版流程。
* 检查按用户要求和任务约定执行。未获要求时不擅自运行测试或构建；发布决策必须以真实验证结果为依据，并列明未覆盖项。

## PR 审查

* “需求价值”与“实现质量”分开判断，分别给结论；实现质量不足不等同于需求无价值。
* 无法确定需求价值时问用户，不凭代码质量/规模推断。
* 实现质量查：正确性、安全、改动范围、重复代码、无关文件、结构复用、可维护性、测试文档、与 `main` 冲突。
* 需求有价值但实现不合格：要求修改/提取思路重做/转入待办，不直接否定需求；关闭 PR 前向用户说明四项（价值/质量/可保留思路/建议处理）并取得确认。
* 合并进 `main` 前说明修复内容、测试结果、风险冲突并取得同意；force-push 他人分支同样先同意。
